`T extends U ? X : Y` selects a type based on an assignability check. With an unresolved type parameter, selection can be deferred until enough type information is available.

```ts
type Label<T> = T extends string ? 'text' : 'other';
type A = Label<string>; // "text"
type B = Label<number>; // "other"
```

## Distribution

A conditional type whose checked type is a naked type parameter distributes over a union supplied for that parameter.

```ts
type ArrayOf<T> = T extends unknown ? T[] : never;
type Distributed = ArrayOf<string | number>; // string[] | number[]
type Together<T> = [T] extends [unknown] ? T[] : never;
type Combined = Together<string | number>; // (string | number)[]
```

Wrapping the parameter prevents that distribution. Distribution over `never` produces no members, so a typical distributive conditional instantiated with `never` evaluates to `never`.

## `infer`

Inside the `extends` pattern, `infer` introduces a type variable for a matched part. That variable is available in the true branch.

```ts
type Element<T> = T extends readonly (infer U)[] ? U : T;
type Name = Element<readonly string[]>; // string
type Returned<T> = T extends (...args: never[]) => infer R ? R : never;
type Count = Returned<() => number>; // number
```

Inference can combine candidates differently according to their positions. Multiple possible matches do not imply a single exact inferred type in every context.

## Overloads and limits

Inferring from an overloaded function generally uses its last signature. Conditional types do not perform call-site overload selection.

Recursive conditional types are subject to instantiation and representation limits. A logically finite construction can still exceed compiler limits, especially when distribution creates many alternatives. Those diagnostics are implementation limits, not additional runtime semantics.

See [conditional types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html) and [diagnostics](/typescript/projects/diagnostics).

## Conditional resolution

A conditional `T extends U ? X : Y` checks a type relationship, not a runtime expression. For a concrete resolvable check, choose the applicable branch. For unresolved parameters, the checker can use permissive instantiations, infer-pattern candidates, and definite relationships to resolve some branches; otherwise it retains a deferred conditional for later substitution.

The original conditional-type procedure distinguishes these decisions:

1. A permissive comparison can establish that the check cannot succeed and select the false branch.
2. Collect candidates for `infer` declarations in the extends pattern.
3. Substitute inferred candidates, combining covariant or contravariant positions as required.
4. If the relevant definite relationship establishes the true branch, select it; otherwise defer.

The implementation also simplifies using constraints and normalized types. This outline is not a claim that every generic `extends` check is decidable by comparing its constraints once. Type parameter constraints and conditional branch refinements have separate roles.

## Distributive instantiation

Distribution applies when the conditional's check is the naked type parameter in the relevant generic definition. Instantiation with `A | B` evaluates constituent checks and unions the results. A tuple, indexed access, or other wrapper prevents that direct distribution.

```ts
type Select<T> = T extends string ? T : never;
type Selected = Select<'a' | 1 | 'b'>;
const selected: Selected = 'b';
// @ts-expect-error: the numeric alternative was filtered
const excluded: Selected = 1;
type Whole<T> = [T] extends [string] ? true : false;
const whole: Whole<string | number> = false;
```

Distribution over `never` visits no constituents and returns `never`. `[never] extends [T]` instead tests the wrapped type as a whole. For a check such as `T extends string ? X : Y`, an `any` argument can produce both branches. Conditions with top-like targets can behave differently; do not specify that any always produces a branch union.

## Infer-pattern declarations

An `infer P` declaration is allowed in an extends pattern and is in scope in the true branch. Candidates from covariant occurrences can combine as a union; candidates from contravariant occurrences can combine as an intersection. No useful candidate can lead to `never` according to the pattern's inference rules. `infer P extends C` additionally constrains the inferred candidate and can determine branch selection.

```ts
type Both<T> = T extends { left: infer U; right: infer U } ? U : never;
const combined: Both<{ left: string; right: number }> = 1;
type NumericText<T> = T extends `${infer N extends number}` ? N : never;
const parsed: NumericText<'42'> = 42;
```

Infer variables are not available in the false branch as successfully matched entities. A repeated infer name represents related candidate inference, not an independent wildcard for each occurrence.

## Overloads, recursion, and evaluation cost

Pattern inference from a callable with multiple signatures ordinarily observes its last signature rather than resolving an overload against a hypothetical argument. Recursive conditionals can express parsers, tuple processing, and Promise unwrapping. Tail-recursive forms receive some implementation optimizations, but distribution and accumulated result size can still exceed limits.

No output code is generated by conditional evaluation. Recursive type complexity affects compiler work and diagnostics rather than runtime execution time.
