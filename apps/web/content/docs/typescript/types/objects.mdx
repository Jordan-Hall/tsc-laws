title: Object types

An object type describes properties and signatures required of a value. Object compatibility is primarily structural: a value can satisfy the type because it has the required shape.

```ts
type User = { name: string; age?: number };
const user: User = { name: 'Ada' };
const age = user.age; // number | undefined
```

## Optional properties

`age?: number` permits the property to be absent. Reads include `undefined` under `strictNullChecks`. With `exactOptionalPropertyTypes`, assigning `undefined` requires the declared property type to include it explicitly.

```ts
// @option: exactOptionalPropertyTypes=true
type Options = { timeout?: number };
const absent: Options = {};
// @ts-expect-error: present undefined is different from an absent property
const present: Options = { timeout: undefined };
```

## Excess property checks

A fresh object literal assigned to a target type is checked for unexpected properties. A variable with extra properties can often be assigned structurally.

```ts
type Named = { name: string };
// @ts-expect-error: an unexpected property on a fresh literal
const direct: Named = { name: 'Ada', age: 36 };
const detailed = { name: 'Ada', age: 36 };
const indirect: Named = detailed;
```

This is not an exact-object guarantee. Other rules, including checks on weak types with only optional properties, can still reject assignments.

## Index signatures

An index signature describes properties accessed through a key family. Explicit properties must be compatible with a relevant index signature. A numeric index value must be compatible with a string index value when both exist, because JavaScript coerces numeric property keys to strings.

With `noUncheckedIndexedAccess`, reading an unspecified key adds `undefined`. Without it, a dictionary annotation can promise a value even when the runtime key is absent.

See [object types](https://www.typescriptlang.org/docs/handbook/2/objects.html) and [strictness](/typescript/projects/strictness).

## Structured type components

An object type can specify named properties, call and construct signatures, index signatures, and generic relationships. A required property must be available on an assignable source with a compatible type. Optional properties may be absent. A property read from an optional member includes `undefined` under strict null checking.

Methods and function-valued properties have different variance behavior. Accessors can have separate read and write types; explicit getter and setter types need not be identical in this edition. See [functions](/typescript/types/functions) and [index signatures](/typescript/types/index-signatures).

## `object`, `{}`, and `Object`

| Spelling | Meaning under strict null checking                                                   |
| -------- | ------------------------------------------------------------------------------------ |
| `object` | Nonprimitive values.                                                                 |
| `{}`     | Any nonnullish value; does not forbid extra properties or primitives.                |
| `Object` | The library interface for Object members, with broadly compatible nonnullish values. |

```ts
const nonnullish: {} = 1;
// @ts-expect-error: number is primitive
const nonprimitive: object = 1;
// @ts-expect-error: null is excluded from the empty object type
const nullish: {} = null;
```

An object type with no declared properties is not an exact empty record. TypeScript does not provide a universal exact-object operator that forbids every unspecified runtime key.

## ExcessPropertyCheck

When a fresh object literal is checked against a target requiring object members:

1. Determine the contextual target and relevant union alternatives, including recognized discriminants.
2. Check explicitly supplied property values and required members.
3. Reject explicit extra properties that are not admitted by the target's members or index signatures.
4. Account for spreads and computed names under object-literal rules.

Assigning an existing variable with additional properties generally uses structural compatibility instead. A spread does not cause every key originating in the spread to receive the same excess-property check as a directly written property. This distinction must not be treated as runtime removal of extra keys.

```ts
type Shape = { name: string };
// @ts-expect-error: an explicit extra property on a fresh literal
const direct: Shape = { name: 'Ada', age: 36 };
const source = { name: 'Ada', age: 36 };
const structural: Shape = source;
const spread: Shape = { ...source };
```

## Weak targets

A weak type has optional properties and no stronger members that establish its shape. Assigning an unrelated object with no common properties can be rejected even when required-property comparison alone would impose no obligation. A compatible common property or an index signature changes that check.

```ts
type Options = { timeout?: number };
const unrelated = { retries: 3 };
// @ts-expect-error: there is no property in common with the weak target
const options: Options = unrelated;
```

## Object literals and spread

An object literal is checked property by property with context where available. Later explicit properties can replace earlier spread properties in the inferred result. A spread does not copy prototypes, nonenumerable members, or class-private declarations into a newly declared nominal entity. Generic spreads can produce intersection-like types because exact runtime keys are not known.

Computed names known as literal or unique-symbol keys can introduce named members. Other computed names can contribute less precise index information. Freshness, contextual typing, and inference jointly determine the literal's result type.
