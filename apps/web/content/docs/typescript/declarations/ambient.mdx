---
title: Ambient declarations
description: Describe values supplied elsewhere with declare and declaration files.
---

An ambient declaration describes a value, type, or module supplied by another implementation. It provides checking information without generating that implementation.

```ts
declare const version: string;
declare function readFile(path: string): Promise<string>;
```

Calling `readFile` still requires an actual runtime function. The declaration does not load it or validate its result.

## Declaration files

A `.d.ts` file describes a public surface. It can represent a module's exports or contribute global declarations. A top-level import or export generally gives it module scope.

```ts
// @filename: library.d.ts
export interface Options {
  timeout?: number;
}
export declare function connect(options: Options): void;
// @filename: main.ts
import { connect } from './library';
connect({ timeout: 1_000 });
```

This checks successfully even though the example includes no runtime implementation. That is the purpose and the boundary of the declaration.

## Ambient modules

An ambient module declaration in a script declaration file can describe a named package. In a module file, a similar declaration can instead be an augmentation of an existing module. The file's context changes its meaning.

Avoid declaring a dependency as unchecked `any` merely to remove an error when a real declaration contract is available.

## Libraries and dependencies

The `lib` option selects default library declarations. `types` restricts which visible `@types` packages enter the global scope automatically. Imports can still bring in types from their resolved dependencies. `typeRoots` changes automatic package discovery locations.

`skipLibCheck` skips checking declaration files internally; it does not remove their types from the program or make their claims correct at runtime.

See [declaration files](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html) and [declaration emit](/typescript/projects/declaration-emit).

## Ambient contexts

An ambient declaration describes an entity whose implementation is supplied elsewhere. A declaration file is ambient; `declare` can introduce an ambient declaration in an ordinary source file. Such declarations participate in binding and checking but do not provide executable JavaScript implementations.

Function and method implementations, executable statements, and arbitrary initializers are prohibited in the applicable ambient contexts. Some constant or enum initializer forms have specific allowances; those do not make an ambient file a source of ordinary runtime initialization.

```ts
declare const version: string;
declare function parse(text: string): number;
declare class Client {
  constructor(url: string);
  readonly url: string;
  send(text: string): Promise<void>;
}
```

Using these declarations relies on a runtime implementing the advertised values. A successful type check alone does not provide `parse` or `Client` to JavaScript.

## Global and module declarations

A declaration file without a module context can contribute global names. A declaration file with imports/exports describes a module environment. `declare module 'name'` in a global declaration context can describe an external module; the same form in a module can be an augmentation with different requirements.

Wildcard ambient modules can model specifier patterns such as asset imports. Their pattern-matching and wildcard restrictions do not make every runtime loader recognize that extension.

## Module augmentation

An augmentation resolves an existing module, then merges compatible named declarations. It cannot freely add new top-level exports or augment a default export through an unnamed entity. A side-effect import may be needed to ensure the implementation being augmented is evaluated, while a type-only reference only affects checking.

```ts
// @filename: model.ts
export interface Item {
  id: string;
}
// @filename: augment.ts
import './model';
declare module './model' {
  interface Item {
    label: string;
  }
}
// @filename: use.ts
import type { Item } from './model';
const item: Item = { id: 'a', label: 'entry' };
```

## Global augmentation and UMD

`declare global` in its permitted module context contributes to global declarations. It does not install runtime properties. `export as namespace` in a declaration file can describe a UMD library's global name for appropriate script consumers. Module consumers and script consumers can therefore see different allowed access forms.

## Declaration dependencies

Triple-slash references, imported types, `types`, type roots, and package resolution determine which ambient declarations enter the program. Multiple libraries can conflict through duplicate globals. `skipLibCheck` suppresses declaration-file checking work, not every consequence of consuming an incompatible declaration type.

An ambient any fallback can mask a missing runtime module or inaccurate schema. Prefer the appropriate typed declaration contract; the specification of module resolution does not guarantee that an ambient declaration matches a loaded package's implementation.
