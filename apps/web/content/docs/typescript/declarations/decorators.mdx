---
title: Decorators
description: Standard decorator behavior, contexts, initialization, and legacy decorator differences.
---

A decorator is applied to a supported declaration and can observe or alter its behavior. TypeScript supports the modern decorator model and a separate legacy model enabled by `experimentalDecorators`.

## Modern method decorators

A method decorator receives the method value and a context. It can return a replacement with a compatible signature. The context describes the decorated member and can provide initialization hooks.

```ts
function logged<This, Args extends unknown[], Return>(
  method: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>,
) {
  return function (this: This, ...args: Args): Return {
    console.log(String(context.name));
    return method.apply(this, args);
  };
}
class Greeter {
  @logged
  greet(name: string) {
    return `Hello, ${name}`;
  }
}
```

Calling `greet` runs the replacement. The declaration can cause emitted helper code; a decorator is not an erased type annotation.

## Initialization and ordering

Decorator expressions are evaluated in their specified order, while stacked decorators are applied in reverse order. A context's `addInitializer` registers work for the appropriate initialization phase. Field decorators, accessors, and classes have distinct contracts; a method decorator is not interchangeable with them.

## Legacy decorators

`experimentalDecorators` selects TypeScript's older decorator implementation, with different arguments and checking behavior. Modern decorators do not support parameter decorators and are not compatible with legacy `emitDecoratorMetadata` behavior.

Libraries written for one model need an implementation that explicitly supports the other model before switching options. The same `@name` spelling does not imply the same runtime contract.

See [TypeScript 5 decorators](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators) and the [legacy decorator reference](https://www.typescriptlang.org/docs/handbook/decorators.html).

## Modern decorator contracts

A modern decorator receives the decorated value (or the field-specific placeholder) and a context describing kind, name, static/private status, access, metadata where supported, and initializer registration. Its accepted replacement depends on the declaration kind.

| Kind          | Permitted result contract                                                          |
| ------------- | ---------------------------------------------------------------------------------- |
| Class         | A compatible replacement constructor or no replacement.                            |
| Method        | A compatible replacement method or no replacement.                                 |
| Getter/setter | A compatible replacement accessor function or no replacement.                      |
| Field         | An initializer transform or no replacement.                                        |
| Auto-accessor | An object with permitted `get`, `set`, and `init` replacements, or no replacement. |

The checker validates the applicable callable relationship. It does not prove that a decorator preserves every runtime invariant of the original class or member. Private-member access uses context-provided access capabilities and private-name semantics, not arbitrary public property lookup.

## Evaluation and application order

Decorator expressions are evaluated in their defined source order, and stacked decorators are applied in reverse order. Replacement and initializer registration are distinct operations. A method's added instance initializers run in the applicable construction phase; field/accessor initialization transforms run at their member initialization point. Static and class initialization have their separate phases.

`addInitializer` must be called within the permitted application period. Registration after that period is not a supported way to add arbitrary later hooks. An initializer's `this` contract follows the decorated entity's initialization context.

## Field and accessor behavior

A field decorator does not directly receive each instance's field value when the decorator expression is applied. It can return an initializer function that transforms the initial value when initialization occurs. An auto-accessor decorator has its distinct getter/setter/storage contract; it is not equivalent to separately decorating an ordinary field and generated method.

TypeScript emits helpers where necessary to preserve these relationships. Decorating an ambient declaration or unsupported declaration position is restricted; a declaration signature alone does not arrange executable decoration.

## Legacy mode

`experimentalDecorators` selects the older TypeScript contracts: class constructors, prototype/constructor targets, property keys, descriptors, and supported parameter decorators. Modern decorators do not support parameter decorators. Legacy `emitDecoratorMetadata` produces its own limited runtime metadata and requires the legacy mode; it is not an implementation of modern decorator context metadata.

Legacy property decorators do not receive and replace field initializers through the same modern field contract. The two systems must be separately documented by a library that supports both.

## Metadata and runtime dependencies

The modern metadata integration described by TypeScript 5.2 uses the supported `Symbol.metadata` environment and context metadata object. Library declarations do not install that symbol or a reflection system. Legacy design metadata likewise does not preserve every generic, union, interface, or source-level type as a runtime schema.

The specification delegates the proposal's runtime operation to the supported decorator model and the edition's transforms rather than claiming that decorators are ordinary erased annotations in ECMA-262's baseline grammar.
