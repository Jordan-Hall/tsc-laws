---
title: Namespaces
description: Named declaration containers and their distinction from file-based modules.
---

A namespace groups declarations under a name. Non-ambient namespaces containing values can produce runtime objects. Members are accessible outside the namespace when exported.

```ts
namespace Geometry {
  export interface Point {
    x: number;
    y: number;
  }
  export function origin(): Point {
    return { x: 0, y: 0 };
  }
}
const point: Geometry.Point = Geometry.origin();
```

## Merging

Namespace declarations with the same name can merge. Exported members are visible across the merged namespace, while non-exported members remain confined to their original declaration body.

```ts
namespace Registry {
  export const version = 1;
}
namespace Registry {
  export type Version = typeof version;
}
const version: Registry.Version = Registry.version;
```

A namespace can also merge with certain value declarations, such as a class, function, or enum, subject to ordering and declaration rules. See [declaration merging](/typescript/declarations/merging).

## Ambient namespaces

`declare namespace` describes a namespace provided elsewhere. It does not create a runtime object. Ambient namespaces are common in declarations for global libraries and some module export patterns.

Declaring a namespace in a module keeps it in that module's scope unless exported or introduced through an explicit global augmentation.

## Modules

A file module already provides a scope and import/export relationships. A namespace wrapping every export inside a module adds another naming layer. Use file modules for ordinary module dependencies; use namespaces when the runtime or declaration contract actually groups members under a value or ambient name.

Compiler options for isolated processing or erasable syntax can impose additional namespace restrictions, because value-containing namespaces require a transform.

See [namespaces](https://www.typescriptlang.org/docs/handbook/namespaces.html) and [namespaces and modules](https://www.typescriptlang.org/docs/handbook/namespaces-and-modules.html).

## Namespace declaration checking

A namespace introduces a qualifying declaration container. Exported members are available through its name; non-exported members remain local under namespace visibility rules. Dotted syntax declares nested namespace structure. The historical identifier-named `module` spelling has namespace behavior and differs from a string-named ambient module.

```ts
namespace Store {
  export interface Item {
    id: string;
  }
  export function create(id: string): Item {
    return { id };
  }
}
const item: Store.Item = Store.create('a');
```

A namespace name does not by itself denote a structural instance type. `typeof Store` queries its value-side object when available; `Store.Item` resolves its exported type name.

## Merging and visibility

Compatible namespace declarations merge their exported members. Non-exported local declarations from one body are not automatically visible in another body. Namespaces can merge with permitted classes, functions, and enums when declaration ordering and kind restrictions are satisfied.

```ts
function create() {
  return 1;
}
namespace create {
  export const version = '1';
}
const version: string = create.version;
```

The merge describes one value with additional exported members; it does not allow two unrelated executable implementations to overwrite one another without restrictions. Type aliases cannot be reopened as namespaces to gain arbitrary merging behavior.

## Runtime representation

A nonambient namespace with value content can emit namespace-object initialization and member assignments. Type-only contents can be elided according to output rules. An ambient namespace describes an externally supplied value or type container and emits no implementation.

The namespace transform must account for existing merged values. It is not equivalent to an ES module import or export. A file containing a namespace can still be a script or external module according to file classification.

## Dependencies and exports

Namespace members use the surrounding lexical environment and permitted internal aliases. Namespaces in global scripts can combine declarations across files, but execution order still matters for runtime initialization. An erased type reference does not schedule the runtime namespace body.

A namespace exported from an external module is available through that module's export environment. It does not automatically become a global variable. `export as namespace` in a declaration file can describe a UMD-style global exposure under its separate ambient rules.

## Restrictions

Ambient namespace bodies prohibit executable statements and ordinary implementations. Runtime namespaces are rejected by `erasableSyntaxOnly`. Independent file transforms require care with cross-file merges and const enum references. The checking contract cannot guarantee that an externally supplied namespace object's runtime members match its declarations.
