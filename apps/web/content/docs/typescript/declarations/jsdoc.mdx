description: Check JavaScript files and describe types with supported JSDoc tags.

TypeScript can include JavaScript files with `allowJs` and check them with `checkJs`. A file-level `// @ts-check` enables checking for an individual JavaScript file. JSDoc comments can describe types without adding TypeScript syntax.

```js
// @ts-check
/**
 * @param {string} name
 * @returns {string}
 */
function greet(name) {
  return name.toUpperCase();
}
```

## Type tags

`@type`, `@param`, and `@returns` annotate values and functions. `@typedef` names a type. `@template` introduces a generic parameter. TypeScript supports type expressions in these tags, including imports used only for checking.

```js
/** @typedef {{ name: string, age?: number }} User */
/** @type {User} */
const user = { name: 'Ada' };
```

Supported JSDoc forms are not identical to every JSDoc tool's syntax. Consult the upstream supported-tag list for constructs your project depends on.

## Assertions and satisfaction

JSDoc can describe a cast attached to a parenthesized expression. `@satisfies` can check an expression against a target type while preserving its inferred type, similarly to TypeScript's `satisfies` operator.

Comments do not perform runtime validation. A cast that incorrectly describes external data can still lead to a runtime error.

## JavaScript inference

JavaScript files have some inference rules different from `.ts` files. Property assignment patterns and missing annotations can be interpreted more permissively. Do not assume that moving the same text to `.ts` produces identical diagnostics.

`allowJs` controls inclusion, while `checkJs` controls reporting of errors in those files. Imported declaration files still affect how JavaScript code is checked.

See [supported JSDoc](https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html) and [checking JavaScript](https://www.typescriptlang.org/docs/handbook/type-checking-javascript-files.html). JavaScript blocks in this reference are explanatory and are not included in the TypeScript example check.

## JavaScript checking context

TypeScript can include JavaScript with `allowJs` and check it with `checkJs` or a recognized `@ts-check` directive. `@ts-nocheck` changes checking as specified by diagnostics rules. These options do not permit arbitrary TypeScript annotation syntax in a `.js` file.

JSDoc provides a comment-based type language interpreted at supported declarations. Attachment, tag spelling, file kind, and surrounding syntax determine whether an annotation applies. A comment placed near an arbitrary expression is not universally a declaration contract.

## Principal tags

| Tag                                              | Checking purpose                                                           |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| `@type`                                          | Annotate a declaration or supported assertion expression.                  |
| `@param` / `@returns`                            | Describe function parameters and results.                                  |
| `@typedef`                                       | Introduce a named type-space alias.                                        |
| `@callback`                                      | Introduce a named callable type.                                           |
| `@template`                                      | Introduce generic parameters, with supported constraints/defaults.         |
| `@extends` / `@augments`                         | Supply supported generic base information.                                 |
| `@implements`                                    | Check a class against a declared contract.                                 |
| `@satisfies`                                     | Check a value against a target without simply replacing its inferred type. |
| `@overload`                                      | Describe supported function overload signatures.                           |
| `@import`                                        | Import type names in a comment without adding runtime evaluation.          |
| `@this`                                          | Describe the applicable receiver.                                          |
| `@public`, `@private`, `@protected`, `@readonly` | Apply supported member checking metadata.                                  |

Type expressions support relevant TypeScript syntax and selected Closure-style forms. Nullable/optional/rest spellings have their documented interpretations; unsupported JSDoc tags are not automatically TypeScript features.

## Imports and generics

An `import('module').Name` type query resolves declarations without a runtime import. TypeScript 5.5's `@import` tag can introduce comment-scoped type imports. `@template` constraints have supported placement rules rather than every tag behaving like a TypeScript generic parameter list with arbitrary independent constraints.

## JavaScript inference differences

JavaScript checking intentionally has differences from `.ts` inference, including flexible object shapes, default treatment of some missing or optional annotations, and property inference from assignments. Constructor-function and CommonJS patterns can contribute declarations. A rule describing strict TypeScript object inference must not be applied unchanged to every checked JavaScript file.

## Output and declaration generation

Comments can affect checking and declaration output without producing validation code. JavaScript input can participate in declaration generation under the appropriate options. Exported inferred shapes may be broader than an explicitly annotated public contract.

JSDoc example text in this clause is not executed by the TypeScript-fence checker. Checking a JavaScript sample requires a JavaScript file and the relevant `allowJs`/`checkJs` context; a TypeScript block containing the same comment does not prove the JavaScript-specific behavior.
