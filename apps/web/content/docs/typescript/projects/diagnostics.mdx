---
title: Diagnostics and suppression
description: Interpret compiler errors, expected errors, and implementation limits.
---

A diagnostic reports a problem found during scanning, parsing, checking, configuration, or emit. It can include a location, code, category, and related information. The source of a diagnostic matters when reducing a reproduction.

## Expected errors

`@ts-expect-error` suppresses a diagnostic on the next line and reports an unused directive when that line has no diagnostic. It is useful for examples and regression tests of rejected operations.

```ts
// @ts-expect-error: number is not assignable to string
const name: string = 42;
```

The directive does not pin an exact diagnostic code or message. If a different error appears on the same line, the directive can still be satisfied. Use more specific compiler tests when the diagnostic identity matters.

## Other directives

`@ts-ignore` suppresses an error without requiring one to exist. `@ts-nocheck` disables semantic checking for a supported file context. These directives do not repair runtime behavior or make the program's annotations reliable.

An explicit `any` can remove checking without appearing as a suppression comment. Include such annotations when investigating why a program is accepted.

## Implementation limits

Errors about excessive type instantiation or an unrepresentable union describe compiler limits. They do not mean a runtime loop has occurred. Distribution, recursive types, and large template-literal combinations can cause a small source file to require substantial type computation.

Simplify the type-level operation or introduce a stable interface boundary rather than suppressing the limit and assuming the intended result was computed.

## Reproductions

Include the source, compiler version, configuration, and dependency declarations. File inclusion and module resolution can be the cause even when an error points to an expression.

Compiler exit status and emitted-file presence are separate evidence. Check [emit](/typescript/projects/emit) before assuming that a file written by the compiler indicates success.

See [TypeScript 3.9 expected-error comments](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#ts-expect-error-comments) and the [TSConfig reference](https://www.typescriptlang.org/tsconfig/).

## Diagnostic categories and phases

A diagnostic can describe configuration, scanning/parsing, binding, global declarations, semantic checking, declaration generation, or other output work. It can carry a code, category, file, span, message chain, and related locations. A file span uses source positions rather than rendered grapheme indices.

Syntax recovery can create secondary errors. Their ordering and elaboration are not fixed by this specification's abstract checking algorithms. Compare primary observations on a minimized program rather than treating every recovery message as a separate language requirement.

## Suppression placement

`@ts-expect-error` and `@ts-ignore` affect the applicable following line. The former requires an error and reports an unused directive when none occurs; the latter can silently remain after the underlying error disappears. Neither requires a particular error code.

A directive on a call can be satisfied by an unrelated arity or unresolved-name error on that line. Rejection examples must therefore keep their setup valid and isolate the intended incompatible operation. Syntax failures, option diagnostics, and errors on other lines are not universally suppressed by the comment.

## File-level checking controls

Recognized leading `@ts-check` and `@ts-nocheck` pragmas control the applicable JavaScript/TypeScript checking context. `noCheck` is a compiler option that can skip substantial semantic work while still performing needed output inference. Declaration checking options have narrower scopes. None of these controls repairs the runtime program.

## Limits and complexity

Excessive instantiation, deep structural comparison, tuple size, and unrepresentable-union diagnostics identify implementation boundaries. Recursive distribution and template cross-products can make small source text require large computations. The diagnostic does not imply a runtime recursive call or give the type expression a different runtime meaning.

Suppressing a limit is not evidence that the desired type was fully computed. Reduce the computation or create an explicit boundary that the implementation can represent.

## CLI observations

Compiler exit status, emitted files, formatted messages, and API diagnostic records are distinct observations. `pretty`, `locale`, and `noErrorTruncation` can alter presentation. `diagnostics`, `extendedDiagnostics`, traces, and profiles provide implementation measurements rather than new typing rules.

An output file existing after a run may be stale or may have been written despite errors. Compare the reported exit and the actual current artifacts. Build mode's error-continuation behavior must be stated separately from ordinary compilation.

## Reproduction record

A useful discrepancy record includes the exact compiler edition, root/configuration selection, effective options, files, dependency/library declarations, module format, and expected observation. For a host-sensitive issue, record casing, symlinks, package conditions, and watch/build state as applicable.

The source of a diagnostic can be outside the line it points to: missing ambient declarations, wrong package conditions, or an unexpected file in the program can change a local expression's type.
