This clause defines the vocabulary used throughout the specification. It applies to the [TypeScript 5.9.3 edition](https://github.com/microsoft/TypeScript/tree/c63de15a992d37f0d6cec03ac7631872838602cb), under the options stated in a clause or the default checking context.

## Requirements and explanation

**Must** states a requirement of the described language behavior. **May** identifies permitted behavior or an explicitly variable result. **Implementation-defined** identifies a decision dependent on the compiler, host, or environment. **Note** introduces explanation rather than an additional checking rule.

These words describe this unofficial specification. They do not imply Microsoft endorsement or tsc-ts certification. When a rule disagrees with the pinned implementation, report the discrepancy rather than treating the prose as authority over that implementation.

An algorithm is an ordered description of an operation on semantic entities. An implementation can use an equivalent procedure. Algorithms describe observable decisions; they do not require a particular cache, representation, or traversal order. A stated implementation limit can end a computation with a diagnostic instead of constructing an unbounded result.

## Source entities

| Term                | Meaning                                                                 |
| ------------------- | ----------------------------------------------------------------------- |
| Source file         | Source text together with its file kind and parse context.              |
| Declaration         | Syntax that introduces an entity or contributes to an existing entity.  |
| Symbol              | The entity associated with one or more compatible declarations.         |
| Binding             | An association between a name and an entity in a scope.                 |
| Value space         | Names usable as expressions, such as variables and constructors.        |
| Type space          | Names usable as types, such as interfaces and type parameters.          |
| Namespace space     | Names that qualify exported names in other declaration spaces.          |
| Ambient declaration | A declaration describing an externally supplied entity.                 |
| External module     | A file treated as a module rather than a global script.                 |
| Checking context    | Options, scope, expected type, and control-flow state used in checking. |

A spelling can denote distinct entities in different spaces. Finding a name is insufficient: the requested meaning must be available. Import aliases and merged declarations require [static semantics](/typescript/specification/static-semantics).

## Grammar notation

The [grammar](/typescript/specification/grammar) uses EBNF:

| Notation          | Meaning                                                       |
| ----------------- | ------------------------------------------------------------- |
| `'token'`         | A terminal token; quotes are notation, not source characters. |
| `A B`             | `A` followed by `B`.                                          |
| `A \| B`          | Either alternative.                                           |
| `[A]`             | An optional occurrence.                                       |
| `{A}`             | Zero or more occurrences.                                     |
| `(A)`             | Grouping.                                                     |
| `ECMAScript:Name` | The corresponding ECMA-262 production or syntactic category.  |

Literal punctuation appears as quoted terminals. Context restrictions accompany productions. Recognizing a production is insufficient for acceptance: invalid modifiers, unavailable names, duplicate bindings, and incompatible types can still produce diagnostics. Automatic semicolon insertion and restricted line breaks follow inherited ECMAScript rules unless a TypeScript production adds a restriction.

Grammar blocks use `text`, not `ts`. They describe syntax rather than runnable programs. The grammar incorporates JavaScript categories by reference instead of reproducing JavaScript's complete grammar.

## Type notation

`S` and `T` denote types; `K` denotes a key type. `S | T` and `S & T` denote TypeScript unions and intersections. A variable in prose is not automatically a source-level generic parameter.

The specification distinguishes identity, assignability, subtyping, comparability, and instantiation. Mutual assignability does not establish type identity. A value assignment performs no runtime membership test. The operations are defined in [type relations](/typescript/type-system/relations).

## Static and dynamic behavior

A **diagnostic** is a compiler observation: a syntax, binding, checking, configuration, or output error. It differs from an ECMAScript exception. An **early error** here is a source restriction diagnosed before evaluation; the compiler need not stop reporting other errors afterward.

**Erasure** removes syntax without a JavaScript representation. **Lowering** produces runtime code for syntax needing a representation at the selected target. **Preservation** keeps syntax for another tool. An annotation is erased; enums, namespaces, decorators, and parameter properties can produce output. See [emit](/typescript/projects/emit).

## Compatibility exceptions

TypeScript permits assignments that a fully sound system would reject, and it imposes finite recursion and representation limits. A type must not be read as proof that an external value satisfies a runtime predicate. These boundaries are specified with the applicable rules, not hidden by an idealized model.
