---
title: Static semantics
description: Binding declarations, resolving names and type syntax, and checking programs before emit.
---

Static semantics gives parsed source a meaning and diagnoses violations of declaration and type rules. The operations below can be performed lazily or combined internally. They do not prescribe a single source traversal.

## BindDeclarations

Given a file and its program:

1. Classify the file using its extension, syntax, and `moduleDetection` option.
2. Establish its global or module scope and nested lexical, function, class, namespace, and type-parameter scopes.
3. Determine each declaration's binding names and declaration spaces.
4. Associate compatible declarations with symbols; diagnose incompatible overlapping declarations.
5. Record members, exports, and declaration-local visibility.
6. Establish control-flow edges needed by checking.

Binding does not establish initializer compatibility. Duplicate declarations and incompatible assignments are separate failures.

## ResolveName

Given a name, location, and requested meaning:

1. Search applicable declarations in the innermost scope, then enclosing scopes and the global environment.
2. Resolve aliases through the target module's exports, preserving type-only restrictions for value uses.
3. For a qualified name, resolve its first component and then members or exports in the requested meaning.
4. Apply visibility restrictions: generic parameter scope, member accessibility, and prohibited use before declaration.
5. Diagnose unresolved names and names available only in another declaration space.

```ts
type Result = { ok: boolean };
function make(): Result {
  return { ok: true };
}
// @ts-expect-error: the alias does not introduce a runtime value
const constructor = Result;
```

## ResolveType

Given a type node and context:

1. Resolve names in type space and type-query names in their query context.
2. Construct primitive and literal types directly.
3. Resolve the components of tuples, arrays, objects, signatures, unions, intersections, and operators under their respective clauses.
4. Apply generic arguments and omitted defaults, validate argument counts, and check constraints.
5. Retain operations deferred by unresolved parameters, then instantiate them when a substitution becomes available.
6. Apply normalization and circularity rules; diagnose illegal aliases or exceeded implementation limits.

Resolving a type does not evaluate JavaScript. A `typeof` query does not invoke or read its queried value at runtime.

## CheckExpression

Given an expression and optional contextual type:

1. Resolve value references and obtain operand and member types.
2. Apply contextual typing where the expression kind supports it.
3. Resolve calls and constructs through applicable signatures and generic inference.
4. Check operations using the relation required by their syntax.
5. Determine the expression's resulting type and recognized flow effect.

Arrays can widen elements, functions can infer return unions, and `satisfies` can provide context without replacing the result type with the target. There is no universal rule that a single expression spelling has a single context-independent type.

## CheckDeclaration

For a declaration:

1. Validate syntactic restrictions and modifier combinations.
2. Resolve an annotation or infer an omitted type from allowed sources.
3. Check initializers, bodies, heritage, overloads, members, and generic constraints.
4. Check definite assignment, returns, accessibility, and merged declaration consistency.
5. Record diagnostics independently of whether output is requested.

Ambient declarations describe externally supplied entities and have separate restrictions on bodies and initializers. They are not arbitrary executable declarations with output disabled.

## Program checking and output

Checking combines configuration, syntactic, global, and semantic diagnostics. Declaration generation can add errors when an exported type cannot be named. `noEmit` suppresses output; `noEmitOnError` determines whether errors suppress it. Neither changes an incompatible assignment into an accepted one.

The abstract operations do not specify secondary diagnostic order or recovery wording. See [diagnostics](/typescript/projects/diagnostics) and [conformance](/typescript/specification/conformance).
