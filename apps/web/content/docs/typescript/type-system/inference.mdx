---
title: Type inference
description: Initializer inference, contextual typing, and generic argument inference.
---

Inference supplies a type when an annotation or type argument is omitted. It uses the expression, candidate types, and surrounding context. The same expression can infer differently in a different context.

## Initializers

```ts
let count = 0; // number
const direction = 'up'; // "up"
const choices = [1, 'two']; // (string | number)[]
```

Mutable locations often widen literals. An empty array or missing initializer has additional inference rules; do not assume it behaves like a nonempty literal.

## Contextual typing

An expected type can supply types inside an expression. Function parameters frequently obtain types this way.

```ts
const names = ['Ada', 'Grace'];
const lengths = names.map((name) => name.length);
// name: string; lengths: number[]
```

Annotating a variable can also provide context to an object literal. `satisfies` checks a target shape while retaining the expression's resulting type, and can influence inference through that context.

## Generic calls

The checker infers type arguments by relating argument expressions to parameter types. Return context can also contribute. Constraints restrict candidates but are not always the inferred result.

```ts
function first<T>(values: readonly T[]): T | undefined {
  return values[0];
}
const value = first(['a', 'b']); // string | undefined
```

## Controlling an inference source

`NoInfer<T>` prevents a position from contributing candidates for `T`, while retaining the type's checking role.

```ts
function choose<T extends string>(values: readonly T[], fallback: NoInfer<T>): T {
  return values[0] ?? fallback;
}
choose(['red', 'blue'], 'red');
// @ts-expect-error: fallback cannot expand the choices inferred from values
choose(['red', 'blue'], 'green');
```

Give explicit type arguments or annotations when inference cannot express the intended contract. See [type inference](https://www.typescriptlang.org/docs/handbook/type-inference.html) and [`NoInfer`](https://www.typescriptlang.org/docs/handbook/utility-types.html#noinfertype).

## InferTypeArguments

For a generic call without a complete explicit argument list:

1. Create an inference variable for each omitted parameter in the applicable signature.
2. Relate argument types to parameter patterns and collect candidates at occurrences of those variables.
3. Use permitted contextual return and expression information, deferring context-sensitive arguments where required.
4. Resolve candidates according to priority and position, including covariant and contravariant combinations.
5. Apply defaults or fallback types where no suitable candidate exists, and enforce instantiated constraints.
6. Recheck arguments against the instantiated signature. A collected candidate is not automatically a successful call.

These steps do not imply a unique most-general solution. The checker uses candidate priorities, fixing points, contextual passes, and heuristics. It can prefer a common compatible type in one location and a union or intersection in another.

```ts
function pair<T>(left: T, right: T): [T, T] {
  return [left, right];
}
const numbers: [number, number] = pair(1, 2);
// @ts-expect-error: the first argument's ordinary inference does not admit string
pair(1, 'two');
const explicit = pair<number | string>(1, 'two');
```

## Candidate position and constraints

A parameter occurring in a return-like or property output position can contribute covariant candidates. A parameter position can contribute contravariant candidates under the relevant signature comparison. Conditional `infer` uses related but distinct combination rules.

A constraint determines what operations a generic implementation may use and bounds permitted type arguments. It is not always the inferred result and does not authorize returning an arbitrary member of the constraint as every possible subtype.

```ts
function keep<T extends { id: string }>(value: T): T {
  return value;
}
const result = keep({ id: 'a', extra: 1 });
const extra: number = result.extra;
```

## Literal and const inference

Ordinary inference can widen literals in mutable or unconstrained positions. A `const` type parameter requests const-like inference for eligible argument expressions. This affects literal object and tuple syntax at the call, not every already-created mutable value. A mutable constraint can force fallback to a wider candidate; readonly constraints are often needed to retain a readonly tuple candidate.

```ts
function tuple<const T extends readonly unknown[]>(value: T): T {
  return value;
}
const result = tuple(['a', 1]);
const exact: readonly ['a', 1] = result;
const existing = ['a', 'b'];
const retained: string[] = tuple(existing);
```

## Context and ordering

Expected return types can contribute inference. Callbacks can require other arguments to determine their parameter types before their bodies can contribute useful candidates. Object method inference has supported left-to-right behavior, so rearranging members or adding annotations can change inferred results.

Unannotated local variables and empty arrays can evolve from recognized assignments. This behavior is distinct from generic call inference and depends on location. A property initialized with an empty array does not automatically inherit the standalone-variable evolving-array rule.

## Blocking and explicit arguments

`NoInfer<T>` preserves checking against `T` while preventing the marked occurrence from contributing inference candidates. It does not remove the occurrence, make the value unchecked, or change runtime output. Explicit arguments bypass inference for supplied parameters; TypeScript does not offer general placeholders for arbitrary partial type-argument inference. Defaults cover omitted trailing arguments under declaration rules.
