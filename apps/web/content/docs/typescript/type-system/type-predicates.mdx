---
title: Type predicates and assertion functions
description: Declared and inferred predicates, assertion signatures, call-site narrowing, and implementation obligations.
---

Type predicates and assertion signatures describe recognized flow effects of calls. They are declaration contracts; a predicate annotation does not cause runtime validation to be generated.

## Predicate syntax and requirements

```text
Predicate = ParameterName 'is' Type | 'this' 'is' Type ;
Assertion = 'asserts' ( ParameterName | 'this' ) [ 'is' Type ] ;
```

A parameter predicate must name an eligible parameter of the signature. Its asserted type must satisfy the parameter's type. Rest parameters and destructured binding patterns have additional restrictions and cannot be treated as arbitrary named predicate targets.

```ts
function isString(value: unknown): value is string {
  return typeof value === 'string';
}
declare const input: string | number;
if (isString(input)) {
  const string: string = input;
} else {
  const number: number = input;
}
```

The true path narrows toward the asserted type; the false path excludes the asserted possibility where the relation permits it. A predicate must describe both outcomes correctly. A test that establishes only a subset on true, such as checking for small numbers, can make a `value is number` annotation misleading on false.

## Body checking and trust boundary

An explicit predicate's body is checked as a Boolean-returning implementation. The checker does not prove that each true result establishes the claimed type or that each false result excludes it. An incorrectly written predicate can therefore create unsound flow facts.

```ts
function incorrectlyClaimsString(value: unknown): value is string {
  return true;
}
```

This is accepted as a declaration contract but is not a correct validator. Predicate correctness for external data requires an implementation appropriate to the claimed structure.

## Inferred predicates

Since TypeScript 5.5, eligible functions can infer a predicate from a recognized single-return Boolean expression, without an explicit return annotation. The function must satisfy inference restrictions, including no mutation of the parameter and a suitable true/false narrowing relationship. An arbitrary Boolean result or a truthiness check with an ambiguous false case does not always infer a predicate.

```ts
const isPresent = (value: string | undefined) => value !== undefined;
const values = ['a', undefined, 'b'].filter(isPresent);
const strings: string[] = values;
```

Library overloads such as `filter` consume predicate signatures. That result depends on both the inferred signature and the selected library declarations. `Boolean` is not a universal substitute for a predicate that excludes precisely nullish alternatives.

## Assertion calls

An assertion signature promises that normal return establishes a condition or type. The function may throw or otherwise fail instead. At a recognized call, `asserts condition` narrows using the condition's truth, while `asserts value is T` narrows the targeted value.

```ts
function assertString(value: unknown): asserts value is string {
  if (typeof value !== 'string') throw new Error('Expected string');
}
declare const data: unknown;
assertString(data);
const text: string = data;
```

Call-target names must satisfy the explicit-declaration requirements for assertion effects. An assertion arrow assigned to a variable may require an explicit function-type annotation on that variable; inferring the callable shape alone does not always make the effect usable. Assertion signatures are not general expression result types and do not turn a returned value into a validator object.

## `this` predicates

Instance members can declare `this is T` or `asserts this is T` to refine a receiver at a recognized use. Unlike a parameter predicate, a `this` predicate is not required to assert a type assignable to the class's instance type. The checker combines the claimed type with the receiver's existing information; the annotation still has the predicate trust boundary.

```ts
class Box {
  value: string | undefined;
  hasValue(): this is this & { value: string } {
    return this.value !== undefined;
  }
}
const box = new Box();
if (box.hasValue()) {
  const value: string = box.value;
}

class IncorrectReceiverGuard {
  isString(): this is string {
    return true;
  }
}
```

The second declaration is accepted; it does not prove that a class instance is a primitive string. A member test can establish a more specific object state only when its implementation supports the claim. Aliases can still invalidate that state at runtime.
