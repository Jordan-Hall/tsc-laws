title: Generics
description: Type parameters, constraints, defaults, and relationships between values.

A generic declaration introduces type parameters that connect its inputs and outputs. A type parameter represents the actual type argument at a use site.

```ts
function identity<T>(value: T): T {
  return value;
}
const text = identity('hello');
const count = identity<number>(3);
```

## Constraints

`T extends U` requires a type argument assignable to `U`. It makes `U`'s supported operations available inside the generic implementation, without turning `T` into exactly `U`.

```ts
function length<T extends { length: number }>(value: T): number {
  return value.length;
}
length('hello');
length([1, 2]);
```

A function returning `T` must return something compatible with the specific `T`, not merely its constraint.

```ts
function keep<T extends { length: number }>(value: T): T {
  // @ts-expect-error: T might require more than a length property
  return { length: value.length };
}
```

## Related parameters

One parameter can constrain another. This expresses relationships such as a key belonging to an object's keys.

```ts
function get<T, K extends keyof T>(value: T, key: K): T[K] {
  return value[key];
}
const name = get({ name: 'Ada', age: 36 }, 'name'); // string
```

## Defaults and const parameters

A type parameter default supplies a type argument when no argument is provided or inferred. Required parameters cannot follow optional parameters with defaults.

A `const` type parameter asks inference to retain literal structure for suitable expressions. It does not freeze runtime values, and a mutable constraint can cause fallback to a wider candidate.

Avoid introducing parameters that do not connect meaningful positions; they can make inference harder without strengthening the contract.

See [generics](https://www.typescriptlang.org/docs/handbook/2/generics.html) and [const type parameters](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters).

## Parameter scope and instantiation

A type parameter introduces a type-space name scoped to its declaration. It can occur in constraints, members, parameters, and returns where available. It creates no runtime parameter, and explicit type arguments are erased.

Instantiation maps parameters to arguments, substitutes them through the declared type, and resolves resulting operations as needed. Aliases, interfaces, classes, and signatures apply their own arity and default rules. Generic class parameters belong to the instance side; static members cannot capture them as per-instance types.

## Constraint checking

For each argument, the checker must verify assignability to the instantiated constraint. Constraints may refer to other parameters. `K extends keyof T` expresses a key relationship and allows indexed access through `T[K]`.

```ts
function get<T, K extends keyof T>(value: T, key: K): T[K] {
  return value[key];
}
const name: string = get({ name: 'Ada', age: 36 }, 'name');
// @ts-expect-error: the argument is not a key of the inferred object
get({ name: 'Ada' }, 'missing');
```

A constrained implementation must work for every admitted argument, not merely the constraint itself. Returning a newly constructed constraint-shaped value can fail because the caller's subtype can require additional members.

```ts
function invalid<T extends { id: string }>(): T {
  // @ts-expect-error: T may require more than the constraint
  return { id: 'a' };
}
```

## Defaults and argument counts

A defaulted parameter is optional in a type-argument list. Required parameters cannot follow defaulted parameters. The default must satisfy the constraint, and earlier parameters may be referenced when constructing later defaults. When no inference candidate is chosen for an omitted defaulted parameter, the default can be used according to the instantiation context.

```ts
type Box<T = string, U = T[]> = { value: T; history: U };
const box: Box = { value: 'a', history: ['a'] };
const numeric: Box<number> = { value: 1, history: [1] };
```

An omitted argument without an applicable default is a diagnostic for an ordinary generic type reference. A bare reference does not universally imply `any`. Generic function calls have separate inference behavior.

## Generic body checking

The body is checked with parameters and their constraints, not rerun independently for every future call. Narrowing a value constrained by a union does not generally rewrite the type parameter itself into a concrete constituent everywhere. Conditional return types involving an unresolved parameter can therefore need implementation structure or an assertion even if callers obtain precise instantiated results.

## Recursive and higher-order types

Parameters can be propagated through nested callbacks, tuple sequences, conditional types, and mapped types. Higher-order function inference can preserve generic relationships in supported patterns. TypeScript does not provide a general higher-kinded type parameter syntax; a parameter cannot simply stand for an arbitrary type constructor applied using `F<T>` without a supported encoding.

Recursive instantiation can be valid but exceed resource limits. Constraints, defaults, and variance annotations are checking metadata, not a way to disable these limits or prove runtime soundness.
