---
title: Assignability
description: When one type can be used in a location expecting another type.
---

An assignment is checked from a source type to a target type. The question is directional: a value that satisfies a narrower set of possibilities can often be used where a wider set is expected, while the reverse use can fail.

```ts
let wide: string | number = 1;
const narrow: number = 1;
wide = narrow;

declare const unknownChoice: string | number;
// @ts-expect-error: the source could be a string
const numberOnly: number = unknownChoice;
```

## Structural object compatibility

An object source generally needs compatible members for the target's required members. Extra source members can remain present.

```ts
type Named = { name: string };
const source = { name: 'Ada', age: 36 };
const target: Named = source;
```

[Fresh object literals](/typescript/types/objects) receive additional excess property checks. Private and protected class members add declaration-origin requirements. A shape-only explanation does not cover those cases.

## Function compatibility

Function parameters and returns are checked using their signature rules. Under `strictFunctionTypes`, function-valued properties have contravariant parameter checks. Method declarations retain a bivariant exception. See [variance](/typescript/type-system/variance).

## Special types and nullability

`unknown` accepts values of other types but needs narrowing before most uses. `any` bypasses much of checking. `never` is assignable to other types because it has no possible values. `strictNullChecks` controls whether nullish values are independently checked.

## Accepted does not mean safe for every execution

TypeScript deliberately permits some operations that a fully sound type system would reject, including certain mutable aliases and callback relationships. Assertions and unchecked external data can also invalidate an annotation's assumptions.

Assignability is a compiler relation, not runtime validation. See [type compatibility](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) for upstream rules and rationale.

## Assignable special and primitive types

Apply the [special-type rules](/typescript/types/any-unknown-never) before assuming ordinary structural comparison. `never` supplies no values and can satisfy other targets; `unknown` accepts other sources but cannot satisfy arbitrary concrete targets; `any` is permissive but cannot satisfy `never`. With strict null checking enabled, nullish alternatives require an admitting target.

A literal can satisfy its corresponding primitive and admitted literal-union target. Unrelated primitive categories are rejected. Enum and unique-symbol relationships include their specific declaration rules, not merely the relationship of their apparent underlying values.

## Union and intersection obligations

A source union requires each possible source alternative to satisfy the target. A target intersection requires all target obligations. A target union can accept a source through an applicable alternative; structured discriminant analysis can also recognize a source whose discriminant possibilities cover compatible target alternatives. It is therefore incomplete to specify every union check as choosing exactly one target constituent for the entire source object.

```ts
type Target = { done: false; value: number } | { done: true; value: number };
declare const source: { done: boolean; value: number };
const accepted: Target = source;
```

A source intersection provides its combined members. It need not have one single constituent containing every target property. Resolving these obligations can require normalization, generic instantiation, and recursive pair comparison.

## CompareProperties

For a structured source and target:

1. For each required target property, find the corresponding source member. An index signature alone does not establish the presence of an arbitrary required named property.
2. Check presence and optionality. A source optional member cannot satisfy a required target merely because its read type happens to be compatible.
3. Compare the member types under the applicable optionality and relation rules. Accessor compatibility uses the read type; a setter's separately declared input type governs writes through that accessor.
4. Apply private/protected declaration-origin requirements where applicable.
5. Check target call, construct, and index signatures with their respective relation rules.

Extra source members ordinarily remain permitted. Fresh object literals additionally receive excess-property checks; weak targets can reject an object without any common member. Readonly ordinary-property modifiers do not create a universal prohibition against mutable aliasing.

```ts
declare const optional: { value?: string };
// @ts-expect-error: optional presence does not satisfy a required property
const required: { value: string | undefined } = optional;

declare const indexed: { [key: string]: number };
// @ts-expect-error: an index signature does not guarantee a named property's presence
const named: { value: number } = indexed;
```

Separate accessor input types do not make object assignment check every possible write through another alias:

```ts
class Source {
  get value(): string {
    return 'text';
  }
  set value(input: string | number) {}
}
class Target {
  get value(): string {
    return 'text';
  }
  set value(input: boolean) {}
}
const target: Target = new Source();
target.value = true;
const read: string = target.value;
```

The compatible read types permit this assignment. The write is checked against `Target`'s setter contract even though the underlying value came from `Source`. This is another aliasing boundary, not proof that the source setter accepts that input at runtime.

## Optional properties and exactness

Without `exactOptionalPropertyTypes`, writing undefined to an optional member is usually admitted through its implicit undefined possibility. With the option enabled, absence and an explicitly present undefined value differ. Reads remain possibly undefined in either mode.

```ts
// @option: exactOptionalPropertyTypes=true
type Options = { label?: string };
const absent: Options = {};
// @ts-expect-error: explicit undefined is not an admitted present value
const present: Options = { label: undefined };
```

The option does not impose exact-object-key checking or ban all extra runtime properties. It changes the write/presence relationship of optional members.

## Signatures, generics, and origins

Each required target overload must have a compatible source signature. Generic signatures require a compatible parameter mapping; replacing all generics by `any` is not a faithful modern description. Function parameter variance depends on method status and `strictFunctionTypes`. Constructor signatures compare instance results and abstract constructability.

Private and protected members require compatible declaration origins. Two unrelated classes cannot satisfy each other's private contract by declaring the same member spelling. Structurally matching public classes remain compatible.

## Comparison limits

Recursive pairs are tracked, and deferred generic operations can be resolved as part of comparison. A comparison may fail because of an instantiation or complexity boundary. The specification does not require a type checker to decide every mathematically representable recursive relationship without resource limits.
