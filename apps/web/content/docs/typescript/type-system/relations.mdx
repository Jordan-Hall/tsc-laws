---
title: Type relations
description: Identity, assignability, subtyping, comparability, and structural signature comparison.
---

TypeScript uses several relations between types. They differ in purpose and in their treatment of special types, optionality, unions, and generic structure. A rule using one relation must not be replaced by a claim that two types simply have the same set of possible runtime values.

## Relation inventory

| Relation         | Operation                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------- |
| Identity         | Compare types without the permissive substitutions of ordinary assignment.                  |
| Assignability    | Check a source against an assignment, parameter, return, or annotation target.              |
| Subtyping        | Use a stricter source/target relationship in selected overload and normalization decisions. |
| Strict subtyping | Support reductions where assignability would discard a distinct alternative.                |
| Comparability    | Determine whether an overlap is sufficient for certain comparisons and assertions.          |

The pinned checker implements separate relation caches. Symmetry is not assumed for source-to-target operations. Even when comparability accepts a pair by considering overlap in either direction, it does not prove that both assignment directions are accepted.

## Identity

Identity accounts for intrinsic kinds, literal values, type parameter identity, type arguments, and the structure of signatures and members. Type aliases do not introduce new nominal identities. Optionality, generic relationships, and property types can distinguish otherwise similar types.

```ts
type A = { id: string };
type B = { id: string };
declare const a: A;
const b: B = a;
```

This assignment establishes compatibility, not an observable runtime type identity. Type-level equality helpers are useful assertions but are not a public API for the checker's identity relation. In particular, an intersection and a flattened object can be mutually assignable while an equality helper distinguishes them.

## Assignability dispatch

For an assignment from `S` to `T`, apply the relevant rules in [assignability](/typescript/type-system/assignability):

1. Resolve deferred types as required and account for identity and special types.
2. Apply source-union and target-intersection obligations.
3. Apply target-union, source-intersection, and discriminant rules.
4. Compare primitive and literal categories, enum restrictions, and type parameter constraints.
5. For structured types, compare properties, index signatures, call signatures, and construct signatures.
6. Apply declaration-origin, fresh-literal, weak-type, and option-dependent checks where applicable.

This is a semantic dispatch outline, not a claim that the checker literally executes six linear passes. A union of object types may be checked through recognized discriminants rather than through a simplistic single-constituent test.

## CompareSignatures

When a source signature must satisfy a target signature:

1. Establish compatible generic instantiations where required by the relation.
2. Check the required parameter count and the allowed arity, expanding tuple rest parameters where applicable.
3. Compare `this` types if both signatures provide a relevant `this` parameter.
4. Compare corresponding parameter types with the appropriate variance rule.
5. Compare return types covariantly, except when a target `void` return discards a returned value.
6. Compare predicates or construct results under their additional requirements.

The target may pass arguments the source ignores, so a function accepting fewer parameters can satisfy one whose callers provide more. A source requiring an additional parameter cannot generally satisfy a target that omits it. Optional and rest parameters have compatibility rules that permit some unsafe substitutions; they do not model every possible JavaScript argument list exactly.

```ts
type Two = (first: number, second: number) => number;
const one = (first: number) => first;
const acceptsTwo: Two = one;

type One = (first: number) => number;
// @ts-expect-error: the second required parameter cannot be supplied by every caller
const requiresTwo: One = (first: number, second: number) => first + second;
```

Under `strictFunctionTypes`, nonmethod function parameters are checked contravariantly. Methods and constructors retain a bivariant exception. Constructors also require compatible instance results and abstract/concrete constructability. See [functions](/typescript/types/functions) and [variance](/typescript/type-system/variance).

## Subtyping and strict subtyping

Subtype relations are stricter than ordinary assignment in cases such as `any` substitution. The checker uses them when candidate ordering or reduction must not make every type interchangeable with `any`. Strict-subtype reduction also preserves distinctions needed for empty object and primitive alternatives.

There is no source-level `subtype` operator. Conditional `extends` types use their own assignability and deferral procedure; class `extends` uses heritage checking; generic `extends` constrains a parameter. Identical spelling does not imply an identical relation.

## Comparability and assertions

An assertion is allowed when the source and target sufficiently overlap according to the assertion checks. A direct conversion between unrelated primitives is rejected, while a conversion through `unknown` can bypass the direct overlap restriction.

```ts
declare const value: string;
// @ts-expect-error: unrelated primitive types do not sufficiently overlap
const direct = value as number;
const indirect = value as unknown as number;
```

The indirect assertion adds no validation. Equality expressions likewise check comparable operand types without proving the comparison true or false for all executions. See [assertions](/typescript/type-system/assertions).

## Recursive comparison

Types can refer to themselves and to recursively instantiated generic types. A checker tracks related pairs and recursion state rather than infinitely expanding them. It can establish a structural relationship coinductively for recurring pairs, but it can also terminate with a depth or complexity diagnostic. Cache and recursion mechanics are implementation behavior, not a source-level nominality rule.
