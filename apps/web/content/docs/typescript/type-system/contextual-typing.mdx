---
title: Contextual typing
description: How expected types contribute to expressions, callbacks, object literals, tuples, and generic inference.
---

A contextual type is an expected type supplied by the surrounding program. It contributes information while an expression is checked; it is not a universal replacement for the expression's result type.

## Context sources

Context can come from an annotated initializer, an assignment target, a parameter of a candidate call signature, an annotated return type, an object member, an array or tuple element, a JSX attribute, or a `satisfies` target. Context propagates only through expression forms that support it. Parentheses ordinarily preserve the relevant context; assigning an expression to an intermediate unannotated variable can lose it.

```ts
type Handler = (value: string) => number;
const contextual: Handler = (value) => value.length;
// @ts-expect-error: there is no expected signature for this standalone initializer
const uncontextual = (value) => value.length;
```

## ContextualizeExpression

Given expression `E` and expected type `T`:

1. Determine whether `E` supports context at its syntactic position.
2. Resolve the relevant property, element, call signature, or return component of `T`.
3. Supply those components to nested expressions, while respecting explicit annotations.
4. Check nested results against applicable requirements.
5. Construct `E`'s result type using its own rules, including literal preservation, freshness, and inference.

Explicit parameter or property annotations impose their own contracts; context does not silently replace an incompatible annotation. A target union supplies context only when the checker can derive an appropriate common or discriminated component. It does not always select the most convenient union alternative for each expression independently.

## Functions and callbacks

A contextually typed function expression or arrow can obtain parameter types and a return expectation from a signature. A context with multiple incompatible signatures can fail to supply one usable parameter type. Generic contextual signatures can transfer parameters where the contextual-signature rules permit it.

```ts
type Callback = (value: { text: string }) => string;
const extract: Callback = (value) => value.text;
// @ts-expect-error: an explicit incompatible parameter is not replaced by context
const invalid: Callback = (value: number) => String(value);
```

The callback's body is checked against the resulting parameters; contextual typing does not execute it or use every caller to infer a new body contract. A `void` contextual result allows discarding a useful returned value under signature compatibility rules.

## Object and array literals

Object context supplies expected types for matching members, which can preserve literals and type nested callbacks. Excess-property checks apply to fresh literals. Array context can distinguish an array of a common element type from a positional tuple. A contextually known discriminant can select the relevant structured alternative.

```ts
type Config = { mode: 'read' | 'write'; transform: (text: string) => number };
const config = { mode: 'read', transform: (text) => text.length } satisfies Config;
const preserved: 'read' = config.mode;
const tuple: [string, number] = ['a', 1];
```

`satisfies` retains the checked expression's result rather than assigning the variable the entire target type. Its context can nevertheless influence that result. It is therefore incorrect to promise that `satisfies` never changes inference.

## Context during inference

Generic calls can check non-context-sensitive arguments first, collect candidates, and revisit callbacks using those candidates. Object member inference can proceed left to right for supported context-sensitive functions. These ordering and priority rules can make equivalent-looking rearrangements infer differently.

```ts
declare function process<T>(options: { produce: () => T; consume: (value: T) => void }): void;
process({
  produce: () => 'text',
  consume: (value) => {
    value.toUpperCase();
  },
});
```

An annotation, explicit type arguments, or an intentional `NoInfer` position can define a contract where inference otherwise lacks sufficient information. Context is one input to inference, not an assertion that every generic parameter is solved optimally.
