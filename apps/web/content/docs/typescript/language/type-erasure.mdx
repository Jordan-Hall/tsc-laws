---
title: Type erasure and runtime behavior
description: Which declarations affect checking and which constructs produce JavaScript.
---

TypeScript annotations, type aliases, and interfaces do not create runtime values. They are removed when the compiler emits JavaScript.

```ts
interface User {
  name: string;
}
type Id = string;

function greet(user: User): string {
  return user.name;
}
```

The emitted function receives an ordinary JavaScript value. It does not automatically validate that the argument has a `name` property.

## Assertions do not convert values

An `as` assertion changes the type seen by the checker. It does not parse, coerce, clone, or validate a value.

```ts
const input: unknown = '42';
const asserted = input as number; // still a string at runtime
const converted = Number(input); // actual conversion
```

Use runtime checks or a validation library for untrusted input. A type annotation on a network response cannot make the response conform to that type.

## Constructs that produce output

Classes, functions, and variables create runtime values. Enums and non-ambient namespaces can also generate runtime objects. Parameter properties can generate assignments. Decorators can produce calls and helper code. JSX is transformed or preserved according to compiler options.

`declare` describes declarations supplied elsewhere; it does not emit their implementation. `import type` is removed. Ordinary imports can remain in output, with their treatment controlled by options such as `verbatimModuleSyntax`.

## Runtime support

`target` selects an output syntax level. `lib` selects declarations for APIs. Including `"DOM"` in `lib` does not install a browser, and including a newer ECMAScript library does not polyfill its APIs.

See [emit](/typescript/projects/emit), [ambient declarations](/typescript/declarations/ambient), and [TypeScript's non-goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals#non-goals).

## Erased syntax inventory

The following constructs have no direct JavaScript representation: type annotations and parameters, type aliases, interfaces, type-only imports/exports, implements clauses, accessibility declarations used only for checking, non-null and definite-assignment assertions, `as`/const assertions, `satisfies`, and type-level operators. Their checking effects can influence diagnostics and declaration output without producing runtime validation.

Abstract member signatures and `declare` fields describe types without ordinary member initialization. Ordinary class members remain runtime syntax; an accessibility keyword being erased does not erase the entire member.

## Runtime-bearing TypeScript constructs

| Construct                       | Output consequence                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| Ordinary enum                   | Runtime object initialization and applicable reverse mappings.                     |
| Namespace with values           | Runtime namespace object/initialization, subject to declaration context.           |
| Parameter property              | Constructor-side property initialization.                                          |
| Decorator                       | Application and initialization behavior with required helpers or preserved syntax. |
| Resource binding                | Disposal handling or preserved supported syntax.                                   |
| Import-equals/export assignment | Module-mode-dependent runtime representation.                                      |
| Const enum                      | References can be inlined; preservation options alter declaration output.          |

These constructs prevent a universal specification of compilation as deleting all type-looking text. A transform must preserve the runtime semantics relevant to the chosen edition and options.

## Erasable syntax checking

`erasableSyntaxOnly`, added in TypeScript 5.8, rejects supported TypeScript syntax requiring runtime semantics beyond straightforward erasure, including enums, runtime namespaces, parameter properties, and import-equals forms. It does not make arbitrary source text safe for a JavaScript runtime that lacks the inherited JavaScript syntax features.

```ts
// @option: erasableSyntaxOnly=true
interface Shape {
  count: number;
}
const shape: Shape = { count: 1 };
// @ts-expect-error: an enum requires runtime-bearing TypeScript output
enum Count {
  One,
}
```

The option differs from `isolatedModules`, which diagnoses patterns unsafe for independent file transforms. It also differs from `noEmit`, which disables output without restricting all runtime-bearing TypeScript syntax.

## Import preservation

`verbatimModuleSyntax` preserves ordinary imports/exports as written while removing marked type-only forms under its module-format requirements. A type-only import is erased even if a runtime module has side effects. A separate side-effect import is needed when evaluation is intended.

Import elision and module lowering otherwise depend on the configured compiler mode. An emitted import specifier is not generally rewritten by `paths`. Resolution and runtime loading must be considered separately.

## Target, helpers, and libraries

Target lowering can introduce helpers for classes, async functions, iteration, decorators, or resource management. `importHelpers` can source helpers from a runtime dependency; `noEmitHelpers` shifts responsibility to the surrounding environment. Types from a library do not polyfill runtime APIs, and a target transform does not validate asserted values.
